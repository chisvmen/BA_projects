Story Statement

As a registered user,
I want to enter and validate my NIP (Numeric Identification PIN) to gain access to the system,
So that only authorised users can access protected resources, and unauthorised access attempts are blocked.

Background & Context

The NIP is a numeric personal identification code used as a second or primary verification factor. It must be validated against a securely stored, hashed value on the server side. The feature covers the full validation flow: input, format checking, server verification, success/failure response, and account lock-out after repeated failed attempts.

Acceptance Criteria

  • 1 Given the user is on the NIP entry screen,
    When they enter a NIP with the correct length and only numeric characters,
    Then the submit action is enabled and the input is accepted for validation.
  • 2 Given the user enters a NIP that contains non-numeric characters or is of incorrect length,
    When the form is submitted (or focus leaves the field),
    Then a clear inline error message is displayed (e.g., "NIP must be exactly 4–6 digits") and the form cannot be submitted.
  • 3 Given the user submits a valid-format NIP,
    When the NIP matches the stored hashed value on the server,
    Then the user is granted access and redirected to the protected area.
  • 4 Given the user submits a valid-format NIP,
    When the NIP does NOT match the stored value,
    Then an error message is shown (e.g., "Incorrect NIP. Try again."), the field is cleared, and the failed-attempt counter is incremented.
  • 5 Given the user has reached the maximum number of consecutive failed attempts (default: 3),
    When the limit is exceeded,
    Then the account is temporarily locked, the user is informed of the lockout duration, and further attempts are blocked until the lockout expires or an admin resets the account.
  • 6 Given a NIP entry is in progress,
    When the characters are displayed,
    Then each character is masked (shown as ●) to prevent shoulder-surfing.
  • 7 Given a failed or successful NIP validation attempt occurs,
    When the event is processed,
    Then an audit log entry is created (timestamp, user ID, outcome) without logging the NIP value itself.

Business Rules

# Rule Priority
BR-01 NIP must be numeric only (digits 0–9); no letters or special characters. MUST
BR-02 NIP length must be between 4 and 6 digits (configurable per environment). MUST
BR-03 Validation must occur server-side; client-side checks are format-only guards, not security controls. MUST
BR-04 The NIP must be stored as a salted cryptographic hash (never in plaintext). MUST
BR-05 After 3 consecutive failed attempts, the account must be locked for a configurable period (default: 15 minutes). MUST
BR-06 The NIP value must never appear in logs, error messages, or API responses. MUST
BR-07 The system should display the remaining attempt count to the user after each failed attempt. SHOULD
BR-08 A "Forgot NIP" recovery flow could be provided via a separate authenticated channel. COULD

Out of Scope

  • NIP creation / change flow (handled by US-NIP-002)
  • Biometric or hardware token authentication
  • Multi-factor combinations beyond NIP (separate epic)
  • Admin panel for managing locked accounts (separate story)

Definition of Done

  • ✓ All 7 acceptance criteria pass in the test environment.
  • ✓ Unit and integration tests cover happy path, format errors, wrong NIP, and account lockout.
  • ✓ Security review confirms hashing, masking, and audit-log compliance.
  • ✓ Accessibility: input field is labelled, error messages are screen-reader accessible.
  • ✓ Product Owner has accepted the story in a demo.

Notes & Dependencies

Dependencies: User account management service must expose a NIP verification endpoint. The lockout mechanism depends on a shared session/rate-limit store (e.g., Redis).

Assumptions: The user is already identified (username or account number) before the NIP screen is shown. The NIP is not a replacement for password-based authentication but acts as a quick-access code in addition to or instead of it, depending on the access policy.

Security Note: Validation response time should be constant (timing-safe comparison) to prevent timing-based attacks on the PIN.
